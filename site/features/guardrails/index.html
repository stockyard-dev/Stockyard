Feature

Guardrails that run in the proxy.

PII redaction, prompt injection detection, and content filtering. Built into the middleware chain, not bolted on as a separate service.

The problem

You are sending user data through an LLM API. Some of that data contains email addresses, phone numbers, or other personally identifiable information. Some users will try to manipulate the model with injection attacks. Some responses will contain content that should not reach your users.

The usual solution is to add a separate guardrail service between your app and the provider. That means another deployment, another failure mode, and another thing to monitor. Stockyard builds guardrails directly into the proxy middleware chain.

What is built in

PII redaction. Detects and redacts patterns for email addresses, phone numbers, and other common PII formats before prompts reach the LLM provider. Configurable per module.

Prompt injection detection. Scans prompts for injection patterns using heuristic scoring. Requests are scored for risk, and you configure thresholds to block, warn, or allow.

Content filtering. Configurable content policies that can block or flag requests and responses based on content type. Runs on both the input and output side of the proxy.

Secret scanning. Detects API keys, passwords, and other secrets in prompts before they are sent to the provider.

Enable at runtime

Each guardrail is a middleware module. Toggle them at runtime without restarting:

# Enable prompt injection detection curl -X PUT http://localhost:7749/api/proxy/modules/promptguard \ -H "X-Admin-Key: $STOCKYARD_ADMIN_KEY" \ -H "Content-Type: application/json" \ -d '{"enabled": true}' # Enable PII redaction curl -X PUT http://localhost:7749/api/proxy/modules/piiredact \ -H "X-Admin-Key: $STOCKYARD_ADMIN_KEY" \ -H "Content-Type: application/json" \ -d '{"enabled": true}'

Changes take effect on the next request. No restart, no config file edit.

Or set them in your config file:

# stockyard.yaml modules: promptguard: enabled: true piiredact: enabled: true toxicfilter: enabled: true secretscan: enabled: true

What guardrails do not do

Guardrails are pattern-based, not model-based. They catch known patterns and heuristic matches, not adversarial attacks designed to evade detection. For high-security environments, guardrails are one layer of defense, not a complete solution. They reduce risk but do not eliminate it.

Safety in the middleware chain.

No external service. No SDK integration. Enable a module and every request is protected.
