Stockyard vs Langfuse

Langfuse is a dedicated LLM observability platform with deep evaluation tools. Stockyard is a self-hosted LLM proxy that includes observability alongside routing, caching, and guardrails. Different tools that overlap on tracing and cost tracking.

The key difference

Langfuse is an observability platform. Stockyard is a proxy that includes observability. This means they solve the tracing problem in fundamentally different ways.

With Langfuse, you add SDK decorators to your application code or configure OpenTelemetry export. Traces are sent asynchronously to Langfuse's backend where they are stored, queried, and evaluated. Your LLM requests still go directly from your app to the provider.

With Stockyard, you point your app at the proxy. Every request that passes through is traced automatically. There is no SDK integration, no decorators, no callbacks. Observability is a side effect of routing through the proxy.

This also means Stockyard can do things Langfuse cannot: cache responses, enforce rate limits, redact PII, detect prompt injection, and fail over between providers. Those capabilities require being in the request path, which a tracing backend is not.

Where Langfuse wins

Evaluation and experimentation. Langfuse has purpose-built tools for LLM evaluation: LLM-as-a-judge scoring, datasets for benchmarking, structured experiments, and quality metrics. If you need to systematically measure and improve output quality, Langfuse is significantly more capable here.

SDK ecosystem. Langfuse integrates with LangChain, LlamaIndex, Vercel AI SDK, and the broader Python/TypeScript ecosystem through decorators and callbacks. If your application is built on these frameworks, Langfuse drops in with minimal friction.

Community and maturity. Langfuse has a large open-source community, was acquired by ClickHouse in early 2026, and is used in production by many teams. There are more resources, more integrations, and more people who can help.

Deeper trace model. Langfuse's hierarchical trace model with nested spans, sessions, and user-level grouping is more expressive than Stockyard's request-level tracing. For complex multi-step agent workflows, Langfuse captures more structure.

MIT license. Langfuse's core is MIT-licensed. Stockyard uses BSL 1.1.

Where Stockyard wins

Zero-instrumentation observability. Route through the proxy and tracing happens automatically. No SDK, no decorators, no code changes beyond swapping one base URL. This matters when you want observability without touching application code.

Proxy capabilities. Caching, rate limiting, failover, guardrails, model aliasing, and cost caps are all built in. Langfuse does not sit in the request path, so it cannot provide these. To get proxy features alongside Langfuse, you typically pair it with LiteLLM, which means running and maintaining two services.

Simpler self-hosting. Stockyard is one binary with embedded SQLite. Langfuse requires PostgreSQL and ClickHouse, typically deployed via Docker Compose or Kubernetes. The operational surface area is meaningfully different.

Audit trail. Stockyard's hash-chained ledger creates a tamper-evident record of every request. Langfuse logs traces but does not provide cryptographic integrity guarantees.

Can you use both?

Yes. Stockyard exports OTEL spans. If you set OTEL_EXPORTER_OTLP_ENDPOINT to point at Langfuse's OpenTelemetry endpoint, you can use Stockyard as the proxy layer and Langfuse for deeper evaluation and analysis. You get automatic tracing from the proxy plus Langfuse's evaluation tools.

The bottom line

If your primary need is deep observability with evaluation, experimentation, and quality scoring, Langfuse is the stronger tool. If you want a self-hosted proxy that handles routing, caching, guardrails, and tracing in one binary, Stockyard covers more of the stack. If you want both, they can work together via OpenTelemetry.
