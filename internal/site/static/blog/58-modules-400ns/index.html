58 Middleware Modules at 400ns

March 22, 2026 · 8 min read

Stockyard runs 66 middleware modules on every LLM request. Rate limiting, cost tracking, caching, PII redaction, content filtering, prompt injection detection, circuit breaking, audit logging — the full stack. The entire chain adds 400 nanoseconds of overhead.

This post explains the architecture that makes that possible: Go function composition, a zero-allocation toggle registry, and why these choices matter when you’re sitting between an application and an LLM provider.

The core primitive

The entire middleware system is built on two types and one function:

// Handler is the core request processing function.
type Handler func(ctx context.Context, req *provider.Request) (*provider.Response, error)

// Middleware wraps a Handler, adding functionality before/after.
type Middleware func(next Handler) Handler

// Chain applies middleware in order. First listed runs first.
func Chain(h Handler, mw ...Middleware) Handler {
    for i := len(mw) - 1; i >= 0; i-- {
        h = mw[i](h)
    }
    return h
}

That’s it. No interfaces to implement. No registry to register with. No lifecycle methods. A middleware is a function that takes a handler and returns a handler. The Chain function composes them right-to-left so the first middleware in the slice runs first on the request.

This matters for performance because the chain is built once at startup. After that, calling the chain is just calling nested functions — there’s no slice iteration, no virtual dispatch, no reflection. The Go compiler inlines the function pointers into a direct call chain.

Why not interfaces?

Most middleware systems define an interface:

// The pattern you see everywhere
type Middleware interface {
    Name() string
    Process(ctx context.Context, req *Request, next Handler) (*Response, error)
}

This is fine for 5 middleware. At 58, the overhead compounds. Every interface call requires a vtable lookup. Every middleware needs its own struct, constructor, and method set. The registry becomes a []Middleware that gets iterated on every request.

With closures, each middleware captures its dependencies at construction time. A rate limiter captures the token bucket. A cache captures the cache store. A cost tracker captures the spend counter. There’s no per-request allocation to look up these dependencies — they’re baked into the closure.

Here’s what a real middleware looks like:

func RateShield(limiter *rate.Limiter) proxy.Middleware {
    return func(next proxy.Handler) proxy.Handler {
        return func(ctx context.Context, req *provider.Request) (*provider.Response, error) {
            if !limiter.Allow() {
                return nil, ErrRateLimited
            }
            return next(ctx, req)
        }
    }
}

The limiter is captured once. Every subsequent call is a direct function call with a single branch. No allocations.

The toggle problem

Static middleware chains are fast but inflexible. Stockyard lets you enable and disable any of the 66 modules at runtime via API call, without restarting the process. This is important for production use — you want to turn off a misbehaving module without dropping traffic.

The naive solution is to check a map on every request for every module. That’s 58 map lookups per request, which gets expensive under contention.

The toggle registry uses sync.RWMutex with an important property: writes (toggling a module) are rare, reads (checking if a module is enabled) happen on every request. RWMutex allows unlimited concurrent readers with zero contention.

type Registry struct {
    mu    sync.RWMutex
    state map[string]bool
}

func (r *Registry) Enabled(name string) bool {
    r.mu.RLock()
    v, ok := r.state[name]
    r.mu.RUnlock()
    if !ok {
        return true  // unknown modules default to enabled
    }
    return v
}

The Wrap function creates a toggle-aware middleware that checks the registry before executing:

func Wrap(name string, reg *Registry, mw proxy.Middleware) proxy.Middleware {
    return func(next proxy.Handler) proxy.Handler {
        inner := mw(next)
        return func(ctx context.Context, req *provider.Request) (*provider.Response, error) {
            if !reg.Enabled(name) {
                return next(ctx, req)  // skip this module
            }
            return inner(ctx, req)
        }
    }
}

The key insight: inner is computed once at chain-build time. The hot path is one RLock, one map lookup, one RUnlock, and one branch. When a module is disabled, we call next directly — the skipped module’s closure is never entered.

The numbers

All benchmarks run on Intel Xeon Platinum 8581C @ 2.10GHz with go test -bench=. -benchmem:

BenchmarkChain58              400 ns/op      0 B/op    0 allocs/op
BenchmarkChain58Toggle       1560 ns/op      0 B/op    0 allocs/op
BenchmarkToggleLookup        23.1 ns/op      0 B/op    0 allocs/op
BenchmarkChain58Parallel    10377 ns/op    192 B/op    2 allocs/op

400ns for 66 modules without toggles. That’s ~6.9ns per module — barely more than a function call.

1.56μs with toggle checks. Each toggle lookup costs 23ns (map access + RLock/RUnlock). Multiply by 58 and you get the expected ~1.3μs overhead on top of the base 400ns.

Under parallel contention (2 vCPUs hitting the chain simultaneously): 10.4μs. The RWMutex holds up well. Only 192 bytes and 2 allocations per request regardless of chain length — those come from the context, not the chain itself.

For context, a typical LLM API call takes 500ms–3,000ms. The middleware chain adds 0.0001% overhead.

What 66 modules actually do

The chain isn’t 58 copies of the same thing. It’s organized into phases that execute in a specific order:

  1. Pre-processing: Authentication, rate limiting, cost caps, input validation, PII redaction
  2. Routing: Provider selection, model mapping, failover, load balancing
  3. Caching: Semantic cache lookup, embedding cache, response deduplication
  4. Safety: Prompt injection detection, content filtering, topic blocking
  5. The actual LLM call
  6. Post-processing: Output filtering, PII re-injection, response transformation
  7. Observability: Trace recording, cost attribution, anomaly detection
  8. Audit: Hash-chained ledger append, compliance logging, webhook dispatch

Order matters. Rate limiting must happen before the LLM call (obvious). But cost tracking must happen after, because you need to know the actual token count. PII redaction must happen before the provider sees the request, but PII re-injection must happen after. The hash-chained audit must be last, because it needs to hash the final state of everything.

Getting this ordering wrong causes subtle bugs. A cache that runs before rate limiting means cached responses bypass rate limits. An audit that runs before post-processing means the ledger records unfiltered content. The chain enforces correctness by construction.

Why this matters for LLM proxies specifically

LLM APIs have a unique property: they’re expensive and slow. A single GPT-4 call might cost $0.03 and take 2 seconds. This changes the economics of middleware.

In a typical web proxy, adding 10μs of middleware overhead to a 5ms database call is a 0.2% tax. Acceptable but noticeable at scale. For an LLM proxy, 10μs on a 2,000ms call is 0.0005%. Irrelevant.

This means you can afford to do more per request. PII redaction that scans every token? Go for it. Semantic similarity checks against a cache? Worth it if it saves a $0.03 API call. Hash-chained audit logging? The integrity guarantee is worth the nanoseconds.

The bottleneck in an LLM proxy is never the middleware. It’s the upstream provider. Our job is to be invisible — add as much functionality as possible without the user ever noticing we’re there.

What I’d do differently

The toggle registry works but it’s the biggest cost in the chain (1.16μs of the total 1.56μs). An atomic.Bool per module instead of a shared map would eliminate the mutex entirely. I haven’t done this yet because 1.56μs is already negligible, and the map gives me a single source of truth for the API to query.

The chain is also rebuilt in full when any module is toggled. A more sophisticated approach would patch the chain in place. But rebuilds happen maybe once a day in production, and the old chain handles in-flight requests until the swap completes (pointer swap is atomic in Go). Not worth optimizing.

If I were starting over, I’d also consider a single-allocation request context that all modules read from and write to, instead of passing *provider.Request and *provider.Response. This would eliminate the 2 allocations that show up under parallel contention. But it would make the middleware signatures uglier, and ugly signatures discourage contribution.

Try it

Stockyard is open source (MIT). The entire middleware chain is in internal/proxy/server.go and internal/engine/engine.go. The toggle registry is in internal/toggle/toggle.go. Read every line — there’s no magic.

curl -fsSL stockyard.dev/install.sh | sh
stockyard serve

# Toggle a module off at runtime:
curl -X PUT localhost:4200/api/proxy/modules/cache -d '{"enabled":false}'

# Check what’s running:
curl localhost:4200/api/proxy/modules

Full benchmark methodology and raw numbers are on the benchmarks page. All numbers are reproducible with go test ./internal/proxy/ -bench=. -benchmem.
